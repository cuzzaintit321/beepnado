Pick the URLs your clients depend on

Start with the public homepage and one high-value page for each client. For a local service business, that could be its booking page. For an online shop, it might be the main catalog. Name each monitor for the client and the page, such as Harbor Bakery · Online menu.

Five clients with two URLs each need ten monitors. That fits within the 20-monitor Pro plan. For a bigger portfolio, count the public URLs you want checked before comparing plans.

Check for the page you expect

A successful HTTP response can still return the wrong page. Set an expected status code or a required phrase when a monitor needs to check for specific content. Use a phrase that belongs on that page and rarely changes. Checks visit public URLs. For a form submission or checkout, monitor the public page and test the actual transaction separately.

Record the outage and the recovery

BeepNado logs failed and successful checks, HTTP status, and response time. Two consecutive failed primary checks open a website incident. Email alerts are available with email delivery configured and a verified account address. During an incident, confirm the affected URL from a separate network before you update the client.

If you need to distinguish a local connection problem from a public outage, use the five-step website downtime checklist.

Share the right status information

A BeepNado account can publish one status page with its active monitor names, current states, and recent incident times. Review the page before sharing it with an individual client. Use names you are comfortable making public.

For a planned deployment, schedule a maintenance window for the affected monitor. BeepNado keeps checking during the window and suppresses outage and recovery alerts for that monitor until it ends.
