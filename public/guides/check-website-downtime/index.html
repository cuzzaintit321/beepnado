Is my website down? A 5-step downtime checklist

Open the exact URL on your phone with Wi-Fi off. If it works on mobile data and fails on Wi-Fi, the problem may be on your local network. If both fail, capture the error and check where the request stopped.

By the BeepNado team at Reboot Syndicate

1. Test the page people actually use

Copy the full URL from the alert, including the hostname and path. A homepage can load while the contact page or storefront fails. Write down the time, time zone, and exact error before refreshing.

Try the same URL on a second network. For a site hosted on your own connection, a LAN test can fail if your router cannot send traffic back through its own public IP. The mobile-data result gives you a separate view.

2. Capture the HTTP response

Replace the sample URL with the page you want to check, then run the command in a terminal.

curl --silent --show-error --max-time 15 --output /dev/null \
  --write-out 'HTTP %{http_code}\n' https://example.com/

A 200 means the request received a successful HTTP response. Open the page and look for the content customers expect. For a redirect, check the destination too. A 503 points to a service that is temporarily unavailable. If curl reports an error with HTTP 000, use the accompanying error to investigate the connection.

3. Separate DNS, HTTPS, and application failures

  • Hostname does not resolve. Check the hostname and its public DNS records, especially after a domain or hosting change.
  • Certificate warning. Check the certificate expiry and confirm it covers the hostname you tested.
  • HTTP 502, 503, or 504. Start with the reverse proxy and the service behind it. Compare their logs at the time of the failed request.

For more detail, see MDN’s HTTP status code reference.

4. Verify recovery from outside

After a fix, check the same URL again from a separate network. If it is a storefront or contact page, confirm the page shows the expected content. Record the first successful check you observe and update your status page with that timestamp.

5. Set up the next check before you need it

Add the public URLs people rely on to an uptime monitor. Keep the alert and recovery history so you can tell when the problem started and when the page came back. For a self-hosted site, use a monitor on another network so it can still report when your home or office connection goes down.
